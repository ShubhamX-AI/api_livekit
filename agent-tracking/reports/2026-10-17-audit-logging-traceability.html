Logging & Traceability Audit

audit · 2026-10-17 · slug 2026-10-17-audit-logging-traceability · report only, no code changed

Trace: scope · research · plan · progress

Asked: are the logs done properly, properly structured, and can a call be traced through them? Partly. The logger module itself is well designed and the worker side traces well, but the SIP bridge processes lose their logs in one deployment and carry no call id in the other, the API has no request tracing at all, and secrets (the MongoDB password, raw exception text) reach the log files.

L-01 · High · Logging not configured in child processes

src/services/outbound_dispatcher/dispatcher.py:53-65 · bridge.py:378 (_bridge_subprocess_entry, target at dispatcher.py:618) · inbound_worker.py:169 · sip_dispatcher_run.py:19

What. SIP bridges run in forkserver children. No bridge module calls setup_logging(). A child is configured only because multiprocessing re-imports the parent's __main__, and sip_dispatcher_run.py:19 happens to call setup_logging() at top level. Gunicorn's main does not. Verified with a probe script: without that top-level call the child's root logger has no handlers, every logger.info is dropped, and warnings come out as a bare message on stderr through logging.lastResort, with no timestamp, level, call_room, or JSON, and never reach LOG_FILE.

Why it matters. When the API process runs the dispatcher (ENABLE_DISPATCHER=true, the default, and the full deployment), every bridge INFO line for every Exotel call is lost. In the dedicated dispatcher container it works by accident; any refactor of sip_dispatcher_run.py silently breaks it there too.

Fix. Call setup_logging() explicitly at the top of both subprocess entry functions (it is idempotent), followed by set_room_context(room_name).

L-02 · High · No call identity on outbound bridge lines

bridge.py (whole run_bridge) · sip_client.py:266-440 · rtp_bridge.py:116-471

What. The outbound bridge never calls set_room_context, so call_room is null. Apart from bridge.py:78 (phone=… room=… rtp_port=…), lines such as [SIP] ❌ SIP/2.0 486 Busy Here or [BRIDGE] Call ended — reason=rtp_silence_after_flow name no room, Call-ID or queue id. Neither formatter prints a pid or process name.

Why it matters. Each outbound call is its own process, and all of them write to the same stdout and file. With a dozen concurrent calls, a SIP failure or RTP silence cannot be tied to the call it happened on.

Fix. Same fix as L-01: set_room_context(room_name) at the start of the bridge process. Add %(process)d to the text format.

L-03 · High · Database credentials in logs

src/core/db/database.py:42

What. logger.info(f"Successfully connected to MongoDB at {settings.MONGODB_URL}"). The URL carries user and password (src/core/config.py:15-16, default admin:secretpassword).

Why it matters. Written at INFO on every process start and on every worker job, into stdout and the rotated files. Anyone with log access has the database password.

Fix. Log only the host and DATABASE_NAME (strip userinfo with urllib.parse.urlsplit). Rotate the password once the line is gone.

L-04 · High · No request tracing in the API

src/api/server.py:114-125, :148-154 · server_run.py:9-19 · src/core/logger.py:169

What. Gunicorn starts without --access-logfile, uvicorn.access is raised to WARNING, no middleware assigns a request id, and http_exception_handler logs nothing. The generic 500 handler (:128-135) logs a trace with no method, path or caller.

Why it matters. A 401, 404, 400 guard rejection or 503 cap refusal leaves no trace unless the route logged first, and most do not. Concurrent requests interleave with nothing to group their lines.

Fix. One HTTP middleware: read or generate X-Request-ID, put it in a ContextVar that _make_log_record stamps like call_room, log method, path, status, duration and key id once per request, echo the id in the response.

L-05 · High · Dispatcher loop can die without a log line

src/services/outbound_dispatcher/dispatcher.py:800-818 · sip_dispatcher_run.py:29, :43

What. _fail_stale_calls_on_startup() and, inside while True, _recover_stuck_dispatching() are outside any try. The task is created at sip_dispatcher_run.py:29 and awaited only at shutdown (:43).

Why it matters. One MongoDB error ends outbound dispatch. Nothing is logged until the container stops, and the process still looks healthy, so queued calls simply never go out.

Fix. Wrap the loop body in try/except Exception: logger.error(…, exc_info=True) and add a done-callback on dispatcher_task that logs its exception.

L-06 · High · SIP listener bind failure is logged and ignored

src/services/exotel/custom_sip_reach/inbound_listener.py:144-145

What. except Exception as e: logger.error(f"[SIP-IN] Failed to bind …: {e}"), then the process carries on.

Why it matters. The dispatcher keeps running with no inbound listener: every inbound INVITE, BYE and CANCEL is lost, and the only evidence is one line at startup.

Fix. Re-raise so the container restarts and health fails; at minimum keep the traceback and expose a health flag.

L-07 · High · Worker session end is not logged reliably

src/core/agents/session.py:1559 · _flush_and_end_call :612-712

What. Agent session ended for room: … is logged immediately after asyncio.create_task(_flush_and_end_call(…)), before teardown runs, and only on the participant-disconnect path. The silence path (voice_features.py:178) and max duration (session.py:1577) log why they end, but the end_call tool path logs no end line, and _flush_and_end_call has no completion line on any path.

Why it matters. "Did this call finish cleanly, and why did it end?" cannot be answered from the worker logs.

Fix. Delete line 1559. Add one INFO line at the end of _flush_and_end_call with end_reason, duration, assistant_id and job id.

L-08 · High · Worker gives up after a single error line

src/core/agents/session.py:285-288, :298-300, :889-894

What. DB connect failure (logged before set_room_context at :293, so no call_room, and no traceback), assistant not found, LLM or STT not built: each logs one line and returns from entrypoint.

Why it matters. The caller hears silence and the log line cannot always be tied to the call. Whether the CallRecord is left non-terminal is suspected, not verified; the dispatcher's silent-call guard (dispatcher.py:347) covers part of this for outbound Exotel only.

Fix. Call set_room_context(ctx.room.name) first thing in entrypoint. Route every early exit through one helper that logs with exc_info, marks the call failed with a reason, and deletes the room.

L-09 · High · Raw exception text logged while the response is redacted

src/api/routes/assistant.py:129 · auth.py:30 · tool.py:43 · sip.py:43, :74 · inbound_context_strategy.py:65 · src/api/server.py:134-135

What. logger.error(f"Failed to create assistant: {e}") and the same shape elsewhere. The HTTP body goes through redact_text; the log line does not. The generic 500 handler logs the unredacted traceback although its own comment (:137-139) says the text can contain a submitted api_key.

Why it matters. A pydantic error from Assistant(**assistant_data) echoes input_value, which can include a provider api_key; a duplicate-key error at auth.py:30 echoes the user email (the lvk_ key is also a unique index, but a collision is negligible). Secrets and personal data reach the log files.

Fix. Log redact_text(str(e)) with exc_info, or add a logging filter that runs redact_text over every message and formatted exception, so no call site can forget.

L-10 · Medium · Several processes write one rotating file

src/core/logger.py:161-167 · docker-compose.yml:18-19, :49

What. Every Gunicorn worker (GUNICORN_WORKERS: "4") opens a RotatingFileHandler on /app/logs/api.log; in the dispatcher container every bridge child opens one on dispatcher.log. The stdlib handler is not multi-process safe.

Why it matters. Each process rotates on its own count: lines are lost, or keep landing in the rotated .1 file.

Fix. Write files only from the main process (or not at all in containers and let Docker collect stdout), or send child records to the parent with a QueueHandler.

L-11 · Medium · Context lives in message text, not fields

374 f-string messages, 0 uses of extra= · dispatcher.py:546-553 · web_call.py:55 · meeting_call.py:65-110

What. call_room is set in three places only (session.py:293, inbound_bridge.py:281, inbound_worker.py:49). The dispatcher and the web and meeting call routes know the room but never set it, so the room exists only as room=… inside the text. JsonFormatter already promotes extra keys, but no call site uses them.

Why it matters. A JSON query on call_room misses every dispatcher and API line for the call; ids can be grepped but not filtered.

Fix. set_room_context(room_name, global_fallback=False) as soon as the room exists in the dispatcher and routes (child tasks inherit it). Move ids (queue_id, assistant_id, tool_id) into extra=.

L-12 · Medium · Worker cannot be joined to the queue item or job

src/core/agents/session.py:294 · dispatcher.py:550-552

What. The start line has room and assistant_id only. ctx.job.id is never logged; the dispatcher does not put queue_id in the job metadata. The only queue_id → room link is one line at dispatcher.py:651.

Why it matters. Following a call from POST /call/outbound to the worker depends on finding that single line.

Fix. Add queue_id to the job metadata and log it, with job_id, call_type and call_service, on the worker start line.

L-13 · Medium · Phone numbers and emails in logs

call.py:21-22, :58-61 · dispatcher.py:622, :651 · session.py:342 · bridge.py:78 · inbound_bridge.py:241, :250, :274 · analytics/admin routes (user email)

What. Caller and callee numbers are logged at INFO on every call; the bridge process is even named bridge-out-{to_number}, so reaper lines leak it too. User emails appear on most request lines.

Why it matters. Personal data spread across stdout and rotated files with no retention control.

Fix. One small masking helper (****1234); name processes after the room; log the key id rather than the email.

L-14 · Medium · Webhook URLs and response bodies logged

src/core/agents/tool_builder.py:181-182 · src/services/livekit/livekit_svc.py:390-437

What. Customer webhook URLs are logged in full at INFO; on a rejected (non-2xx) response, the end-call webhook logs up to 500 chars of the receiver's body (livekit_svc.py:421-423); tool arguments are logged at DEBUG.

Why it matters. Webhook URLs often carry a token in the query string; responses and tool arguments can echo caller data.

Fix. Log only scheme and host; drop the body (ActivityLog already stores it); log argument keys only.

L-15 · Medium · Errors logged without a traceback

123 logger.error vs 27 exc_info and 1 logger.exception · e.g. dispatcher.py:305, :351, :481, :498 · inbound_bridge.py:284, :306, :348 · tool_builder.py:70, :232 · session.py:450 · llm/factory.py:144-151 · database.py:65

What. Failures on finalize, webhook, setup, tool build and transcript paths are logged as str(e), which for TimeoutError() and similar is empty.

Why it matters. The line says something failed but not where or why.

Fix. logger.exception(…) or exc_info=True on every error path that is not an expected outcome.

L-16 · Medium · Analytics and admin errors logged twice

analytics.py:114, :185, :249, :308, :361 · admin.py:58, :121, :181, :229, :268, :356, :427

What. except Exception as e: logger.error(f"[…] failed for {email}: {e}"); raise, then the generic handler logs it again.

Why it matters. Two ERROR lines per failure, the first without a stack.

Fix. Delete these try/except blocks; the global handler already covers them.

L-17 · Medium · SIP monitor and BYE failures swallowed

sip_client.py:431-432, :441-442 · bridge.py:304-307, :357

What. Any exception in wait_for_disconnection is logged at INFO as Monitor ended; the bridge then records sip_bye_outbound_tcp and sets ended_by_remote_bye=True, so no BYE is sent. send_bye has except Exception: pass.

Why it matters. The logged end reason is false, and a failed or skipped BYE (an Exotel leg still up and billing) leaves no trace.

Fix. Log at WARNING with exc_info; return the real reason and set ended_by_remote_bye only on a BYE; warn when send_bye fails.

L-18 · Medium · Silent failures in the worker

session.py:1262-1263, :1614-1620, :1250-1257 · voice_features.py:85-86, :350-351 · tts/factory.py:217-218 · dispatcher.py:585, :625, :637, :734

What. A malformed call_answered packet is dropped with pass (the logs show only the later 60 s timeout); filler words stop with nothing logged; the Sarvam keepalive failure is DEBUG only; fire-and-forget tasks have no done-callback; the try around create_task at :1614 can never catch the task's error.

Why it matters. Features stop working and the only symptom is the call itself.

Fix. Log at WARNING with exc_info (once per call where noisy); one _spawn(coro, what) helper that logs task.exception().

L-19 · Medium · Wrong levels for expected outcomes

sip_client.py:365 · bridge.py:188 · src/api/server.py:102

What. 486 Busy, 480 and 603 are logged at ERROR; every client 422 is logged at ERROR.

Why it matters. Normal outcomes flood error alerting and hide real faults.

Fix. INFO or WARNING for busy, no answer, rejected and validation errors; ERROR for 5xx and genuine failures.

L-20 · Medium · Per-packet error logging on the RTP path

rtp_bridge.py:320, :426, :272, :284

What. [RTP] Decode error logs a full traceback per packet; [RTP] Send error logs per 20 ms frame.

Why it matters. A persistent fault produces about 50 lines a second per call, with tracebacks.

Fix. Log the first occurrence with exc_info, count the rest, and report the counts in the existing stop summary (:461).

L-21 · Medium · Bridge config failure reported as a timeout

bridge.py:59-64 · dispatcher.py:425-438

What. if not validate_config(): return without _send_result. The parent waits and records Exotel SIP setup timed out.

Why it matters. The CallRecord and dispatcher log state the wrong cause; the real one is only in the child's log, which L-01 may have dropped.

Fix. Send a failure result naming the config problem before returning.

L-22 · Medium · Inbound connection errors at INFO

inbound_listener.py:315-316

What. except Exception as e: logger.info(f"[SIP-IN] Connection ended: {e}") covers both a normal close and a parser bug that drops every dialog on the connection.

Why it matters. Real faults look like normal hang-ups.

Fix. Connection errors at INFO; anything else at WARNING with exc_info.

L-23 · Medium · Production writes coloured text to stdout

src/core/config.py:30 · docker-compose.yml · src/core/logger.py:74

What. LOG_JSON_FORMAT defaults to false and docker-compose does not set it, so container stdout is ANSI-coloured text. The text format has no call_room.

Why it matters. Whatever collects container stdout gets escape codes and no call id; only the file handler is JSON.

Fix. Set LOG_JSON_FORMAT=true in every deployed service; add [%(call_room)s] to the text format for development.

L-24 · Low · Two logger naming schemes

database.py:19 · tool_builder.py:21 · utils.py:4 · inbound_context.py:9 · smtp_service.py:8

What. Most modules use the shared app logger; these use getLogger(__name__).

Why it matters. A filter on logger=app misses tool, inbound-context and DB lines; the logger field does not identify the module consistently.

Fix. Pick one: either everything on getLogger(__name__) (the stdlib idiom, and module is already in the JSON) or everything on app.

L-25 · Low · Steady INFO noise

dispatcher.py:690-694, :757, :777 · inbound_listener.py:285-287 · bridge.py:75

What. "No slots available" on every tick while at capacity; a change-stream line for every call end; one INFO per Exotel OPTIONS keep-alive; every bridge child logs [PortPool] Ready with 500 ports.

Why it matters. Volume hides the lines that matter.

Fix. DEBUG when nothing happened; build the port pool only when the child owns the port.

L-26 · Low · Lines that name no entity

auth.py:15, :25, :33 · assistant.py:78, :119 · call.py:251 · web_call.py:46 · meeting_call.py:60 · dispatcher.py:188-190 · livekit_svc.py recording lines

What. "API key created successfully", "Received payload after end call", "recovered N stuck queue item(s)" with no ids.

Why it matters. Each tells you that something happened but not to what.

Fix. Add the id the line is about; delete lines the access log (L-04) will cover.

L-27 · Low · Raw exception text persisted to records

dispatcher.py:659, :518 · bridge.py:350

What. item.last_error = str(e) and Monitor error: {e} are stored and can be returned by GET /call/queue/{id} or the end-call webhook.

Why it matters. Same leak as L-09, but at rest and visible to API callers.

L-28 · Low · Auth failures and unpriced usage leave no log

src/api/dependencies/auth.py:21-26 · src/core/pricing/calculator.py:76-80

What. A 401 is raised with no log; an unpriced model is flagged in data but never logged.

Why it matters. Key-guessing attempts and pricing gaps are invisible until someone queries for them.

Fix. One INFO line on auth rejection (key prefix only); one WARNING per unpriced provider and model.

7. What is done well

  • call_room is stamped at record creation, so it survives LiveKit's IPC pickle and reaches callbacks and plugin tasks in the worker; the job_proc early return prevents duplicated lines.
  • The dispatcher-side inbound path uses a task-scoped ContextVar (global_fallback=False), correct for a process that interleaves calls.
  • 422 bodies and their log line are built from loc/msg only, with secret inputs masked; every HTTP error body goes through redact_text.
  • SIP digest headers, full SIP messages, LiveKit JWTs and S3 keys are never logged.
  • LLM build lines log model and knobs, exclude api_key, and print the replay command; config-drop warnings name the value and the fix.
  • RTP logs first RX/TX once and a summary at stop, not per packet (except the error paths in L-20).
  • No print() in shipped code paths; openai_live caches by key fingerprint and never logs the key.
