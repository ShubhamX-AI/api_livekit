End-of-call webhook and Mongo payloads

Version 1.7.0. Every JSON block below was produced by running the real code: the SDK usage collector, summarize_usage, price_model_usage and LiveKitService.send_end_call_webhook with the HTTP client and database stubbed. Only the sample inputs (a 2.5 minute outbound Exotel call, names, ids, numbers) are made up. Cost strings are shown exactly as produced, with all their digits.

1. The webhook call

call ends→read CallRecord + UsageRecord→build one JSON body→POST to the end-call URL→write an activity_logs row
ItemBehaviour
WhenAt the end of the call (end_call), and for outbound calls that never connect (busy, no answer, rejected and similar, from the dispatcher). Nothing is sent if there is no call record or no URL.
URLA webhook_url passed in (passthrough trunks), else the assistant's assistant_end_call_url.
RequestPOST, JSON body, Content-Type: application/json. No authentication header is added.
Body shape{"success": true, "message": "Call details fetched successfully", "data": {...call record fields..., "usage": {...}}}. data is the call record without its Mongo id. usage is present only when a usage record exists.
TimeoutsRead timeout END_CALL_WEBHOOK_TIMEOUT (default 30 s), connect timeout 10 s. The assistant's assistant_end_call_webhook.timeout_seconds overrides the read timeout.
AttemptsEND_CALL_WEBHOOK_ATTEMPTS (default 3), or the assistant's assistant_end_call_webhook.attempts. Backoff 1 s, 2 s, 4 s.
RetriedTimeouts, transport errors, HTTP 429 and 5xx.
Not retriedAny other 4xx. A 2xx is success.
ResultOne activity_logs row per delivery (success or error), with the URL and the receiver's status code and first 500 characters of its reply. The payload itself is not stored there.

Example activity_logs document for a successful delivery (the same shape in every mode; latency_ms is a sample):

{
  "user_email": "owner@example.com",
  "log_type": "end_call_webhook",
  "assistant_id": "a7242fb5-3fae-44d1-942a-a21368fcf3c8",
  "room_name": "room-duplex-7f3a",
  "status": "success",
  "request_data": {
    "url": "https://hooks.example.com/call-ended"
  },
  "response_data": {
    "status_code": 200,
    "body": "{\"received\": true}"
  },
  "latency_ms": 143,
  "message": "Post-call data sent to https://hooks.example.com/call-ended (HTTP 200)"
}

2. The standard cost format

Every mode reports cost the same way: one model_usage entry per billed model, each with its own estimated_cost_usd, and estimated_cost_usd on usage is their sum. There are no mode-specific cost fields. Each part has its own type: stt_usage, llm_usage and tts_usage for cascade and pipeline, llm_usage for realtime, and voice_llm_usage (GPT-Live) with backend_llm_usage (its backend model) for duplex. The worker also writes one log line per call, for example:

Cost by model | room=room-duplex-7f3a | gpt-live-1=$0.125000 | gpt-6-luna-2026-09-30=$0.000310

4. Webhook compared with Mongo

call fields: the webhook data carries the whole call_records document except _id, so the two match field for field. Dates are ISO strings in the webhook.

usage fields: the webhook usage object is a hand-picked list of fields from the usage_records document, not the whole document. These Mongo fields are not in the webhook:

_id, assistant_id, created_at, room_name, user_email

The assistant call logs endpoint (GET /assistant/.../logs, field data.logs[].usage) and GET /call/records/{room_name}/usage return the whole usage_records document, so they include those fields.

Cost fields: in all four places (webhook, Mongo, call logs, usage endpoint) the cost is in model_usage and the total in estimated_cost_usd. For an entry with no rate, estimated_cost_usd is absent on that entry, pricing_complete is false and the entry is also in unpriced_model_usage.
