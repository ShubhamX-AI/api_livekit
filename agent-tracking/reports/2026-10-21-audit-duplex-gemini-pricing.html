Summary

Duplex pricing: with the default tier, the backend model is priced and added to the GPT-Live voice seconds (simulated end to end, below). Backend cost goes missing in three cases: any non-default service_tier, a backend snapshot name the code does not recognise, and in the display, because the cost is only a total with no labelled backend line.

Gemini: models, voices and rates match the plugin, the LiveKit docs and Google's pricing page. Two real defects: settings that Gemini ignores are accepted without error, and thinking tokens are never counted, so extended-thinking calls are under-priced. I could not reproduce a Gemini error offline; I need a log line to pin it (see Gemini error).

Findings

D-01 · High · Bug: wrong scope for the tier guard · src/core/pricing/calculator.py:73-75, src/core/agents/session.py:502-505

Any service_tier other than auto/default sets the rate to None for every OpenAI llm_usage entry. In duplex the tier belongs to the backend only (responses_options), yet the voice entry gpt-live-1 is unpriced too. Reproduced: tier fast, flex or priority gives cost 0, pricing_complete false, both models in unpriced_model_usage.

Why it matters: a duplex assistant with a tier shows no cost at all, which is what "backend pricing missing" looks like. The tiers are priceable: OpenAI's page today lists flex at 0.5x and fast (formerly priority) at 2x for gpt-6-luna, gpt-6-sol and gpt-5.6-luna.

Fix: apply the tier only to the backend entry, never to a session_second rate, and price it with a per-tier multiplier (flex 0.5, fast/priority 2.0) instead of dropping to unpriced. Add a test: duplex + flex still prices the voice entry.

G-01 · High · Silent no-op settings (guardrail violated) · src/core/agents/session.py:870-877, src/api/models/api_schemas/config/llm_config.py:322-335

Gemini realtime is built from model, voice, modalities, instructions, api_key only. The mode table checks model and voice, nothing else. Probe: temperature, max_output_tokens, reasoning_effort, verbosity, service_tier, tool_choice all pass validate_mode_config("realtime", gemini) and none reach Gemini.

Why it matters: AGENTS.md guardrail says knobs a model ignores are a 422. Here the operator believes they set a temperature or a reasoning effort and nothing happens. The plugin does accept temperature, max_output_tokens, top_p and thinking_config; the docs say gemini-3.8-live-extended-thinking takes thinking_level low/medium/high (default low) and gemini-3.8-live takes none.

Fix: in the realtime/gemini branch, 422 the OpenAI-only knobs; forward temperature and max_output_tokens; add a Gemini thinking_level accepted only on the extended-thinking model. Update docs/reference/compatibility.md.

G-02 · Medium · Thinking tokens never metered, estimate silently low · .venv/.../google/realtime/realtime_api.py:1648-1650, src/core/pricing/rates.py:177-181

The plugin reports response_token_count as output. google-genai's UsageMetadata has thoughts_token_count and tool_use_prompt_token_count; the plugin never reads them. Google's page prices output "including thinking tokens". The rate-table comment says thinking needs no separate rate, which is true for the rate but hides that the count never arrives. pricing_complete stays true.

Why it matters: gemini-3.8-live-extended-thinking calls report a cost below the real bill, with no flag. Suspected from source; confirming needs one live call (already an open question in the earlier Gemini plan).

Fix: wrap or subclass the realtime session to add thoughts_token_count to output tokens; until then mark extended-thinking cost as a floor (pricing_complete=False or a note field) so it is not read as exact.

D-03 · Medium · Backend cost not shown as its own line · src/core/agents/session.py:575, src/services/livekit/livekit_svc.py:521-526

The end-call webhook sends estimated_cost_usd (one total) and a model_usage array in which each entry has its own cost. The flat llm_input_tokens/llm_output_tokens hold backend tokens while llm_session_duration holds voice seconds. Nothing labels which entry is the backend, and the "Usage persisted" log line prints only the total.

Why it matters: this is the gap you describe: the backend price is inside the data but a reader of the log or webhook cannot see it.

Fix: in duplex add llm_backend_model plus estimated_cost_voice_usd and estimated_cost_backend_usd to the webhook usage block, and print both in the log line. Derive them from model_usage; no new storage is required.

D-02 · Medium · Snapshot fallback matches one name shape only · src/core/pricing/rates.py:212-213, 235-237

OpenAI reports the backend under the snapshot that served it. Only <alias>-YYYY-MM-DD falls back to the alias rate. gpt-6-luna-20261001 and gpt-6-luna-2026-10-01-preview come back unpriced (reproduced); gpt-6-sol-2026-10-01 prices.

Why it matters: one unexpected snapshot spelling zeroes the backend cost. It is visible only as pricing_complete: false.

Fix: log a WARNING with the unmatched model name at persist time, and accept a compact -YYYYMMDD form. Do not widen further, as the existing comment explains.

G-03 · Medium · Greeting through a private method, no guard · src/core/agents/session.py:1754-1760

The Gemini greeting calls agent_instance.realtime_llm_session and rt_session._send_client_event(...) directly. realtime_llm_session raises RuntimeError("no realtime LLM session") if the activity is not ready, and the Gemini branch has no try, unlike the duplex and OpenAI branches. It also skips allow_interruptions and the speech handle. The LiveKit docs say generate_reply() works on 3.1/3.8 with plugin 1.8.2 or later (pinned 1.8.8).

Why it matters: a failure here ends the greeting with a traceback; it is the one place in the Gemini path I found that can raise at call start. Suspected, not reproduced.

Fix: use session.generate_reply(instructions=...) like the other modes, or wrap the call and log. Test on a live Gemini call before removing the workaround.

G-04 · Medium · Extended thinking and tools unverified · src/core/agents/session.py:870

No thinking_config is set, so gemini-3.8-live-extended-thinking runs at the plugin default (low). The earlier plan left open whether that model accepts tools without an explicit tool behavior; the plugin defaults non-blocking for any "3.8" model name. Unverified without a live call.

Fix: run one live call with a tool on each 3.8 model before advertising extended thinking.
